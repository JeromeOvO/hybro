# A2A 1.0 接入与 SDK 迁移计划

状态：待实施。本文描述目标设计和验收要求，不表示这些能力已经实现或通过测试。

## 1. 目标与已确认决策

主要目标是让 Hybro 能发现、注册并调用遵循 A2A 1.0 协议的外部 agents。四个默认 agents（Story、Travel Planner、Image Generator、Weather）统一迁移为 1.0 agents。

实施顺序：

1. 在现有 SDK 上补齐协议隔离，保持现有行为。
2. 升级 SDK，接入协议 1.0，复用官方 0.3 兼容能力。
3. 迁移全部默认 agents，完成 1.0 端到端验证。

0.3.0 不是完整兼容承诺：只依赖官方 SDK 的兼容层，保留轻量冒烟测试，不维护自研旧协议实现或完整双版本测试矩阵。默认 agents 不需要额外暴露 0.3 服务端接口。

最小设计原则：复用已有 DTO、Protocol、receipt、observation、仓储和组合根；只增加本次真实消费者需要的字段及转换。目标是限制未来协议升级的影响，不是建立支持任意协议的框架。

## 2. 当前基础与问题

以下是调研时的工作树状态，实施前需要重新核对，尤其注意并行开发中的未提交修改：

- 后端 `backend/pyproject.toml` 约束为 `a2a-sdk>=0.3.25,<1`，`backend/uv.lock` 锁定 0.3.25。
- SDK 依赖主要集中在 `backend/a2a_adapter/`，Execution 已拥有 A2A 响应摄取和最终处理职责。
- 生产调用包括 `client_facade`、`remote_task`、`orchestrator_direct_client`，另有 runtime service 和 transport 路径。不能只迁移一个 send 函数就认为接入完成。
- `backend/common/types.py` 的内部类型仍保留旧协议结构；`message_factory.py` 等依赖 `model_dump()` / `model_validate()` 的结构相似性转换。
- Card 解析依赖旧版 SDK 校验与顶层 URL；HITL 某些回复路径只传 URL，未完整表达选定接口。
- `webhook_payloads.py` 的部分 proto 形状兼容不等于 1.0 合规：递归改写字典键可能改变业务 metadata；把事件过早压成 Task 可能丢失 artifact 更新语义。
- Story、Travel 的 SDK 约束低于 0.3；Image 使用 0.3 系列；Weather 使用第三方 `a2a-adapter[langchain]`。不能把它们都当作 0.3.0 agent。

核心问题是内部逻辑依赖 SDK 表示方式，而不是所有旧字段名称都必须消失。例如内部保留 `kind` 或小写任务状态可以是合理的产品契约，但不能直接假定它们等于新版 SDK 的 wire schema。

## 3. 目标边界与不变量

```text
Frontend / Room / Execution / Orchestrator
                    ↕ Hybro 内部契约
                a2a_adapter
                    ↕ 显式转换
                A2A SDK 1.x
                 ├─ 原生 1.0 transport → 1.0 agents
                 └─ 官方 0.3 compat   → 0.3 agents
```

### 必须保持

- Execution 继续拥有响应摄取、去重、任务生命周期和最终落库；adapter 只负责协议、网络和到内部契约的转换。
- 业务层不消费 SDK 对象、Protobuf 类型、JSON-RPC envelope 或 SDK `.root`。
- 保留 `client_request_id`、message/command identity、远端 task/context identity 及既有调用绑定；协议版本不是新的业务身份。
- 保留 HITL interaction metadata、回答关联与续传身份。回复原任务不能退化为创建新任务。
- metadata 和结构化业务数据的键和值按既有契约原样传递；不使用通用递归 camelCase/snake_case 转换。
- 保留 artifact ID、追加/替换语义及适用的分块完成信息；继续经过现有文件大小、内容校验和存储安全边界。
- 区分任务终态、交互暂停、流正常结束、网络中断和协议错误。流关闭不等于任务成功。
- 不增加 adapter 自有业务重试、任务状态机或第二个事件最终处理者。
- 保持现有前端 REST/SSE 与历史持久化语义。若必须改变公开契约或历史数据兼容，先确认再实施。

### 不做

- 不重写 Orchestrator kernel、Room、前端 SSE 或全面转换历史数据库消息为 ProtoJSON。
- 不引入通用协议基类、插件注册系统、自研双协议框架或 SDK 双版本安装方案。
- 不为形式上的中立性批量重命名内部字段，不顺带删除未经确认的历史功能。
- 不因本次升级新增 gRPC、REST transport、多租户、ListTasks 等能力；先保持现有 JSON-RPC/HTTP/SSE 接入范围。
- 不通过“1.0 调用失败后换 0.3 重发”实现兼容，避免重复远端副作用。
- 不承诺 0.2 或更早协议，也不为 0.3 建立完整回归矩阵。

## 4. 阶段一：补齐隔离，暂不升级 SDK

### 工作内容

1. 核对实际调用链与现有测试，建立 send、stream、get、cancel、HITL、Card、webhook 的边界清单。完整阅读待改文件，不只依赖架构文档的历史描述。
2. 复用内部输入与结果模型，把 SDK 请求构造、响应解包、异常识别全部留在 adapter。仅为确实缺失的 task identity、接口信息或事件语义扩展既有模型。
3. 将隐式 dump/validate 跨层转换替换为明确字段映射。内部模型可继续使用 Pydantic，但不承担识别任意 SDK 对象的职责。
4. Card 对外提供 Hybro 消费者所需的描述与可调用接口信息。原始协议 Card 如需保存，作为边界数据处理，业务流程不从任意原始字段猜 endpoint。
5. 在流和 webhook 转换处保留必要事件差异，再交给既有 Execution 处理；不要为了复用提前抹掉 append/replace 或身份信息。
6. 覆盖当前使用 SDK 类型的测试 fixtures、注入接口和 SDK confinement 检查；不另建平行的内部模型体系。

### 主要文件范围

- `backend/common/types.py`、现有相关 DTO 和 Protocol。
- `backend/a2a_adapter/message_factory.py`、`translators.py`、`client_facade.py`。
- `backend/a2a_adapter/card_data.py`、`card_resolver.py`、Card 校验/健康/inspection 模块。
- `backend/a2a_adapter/webhook_payloads.py`、`transport.py`、`remote_task.py`、`task_requests.py`。
- `backend/a2a_adapter/runtime_service.py`、`orchestrator_direct_client.py`。
- 必要的 `backend/orchestrator_composition.py`、Execution 消费者和测试。

这是检查范围，不是要求修改全部文件。模块是否仍在使用，以实施时调用证据为准。

### 阶段验收

- SDK 仍为 0.3.25，既有业务行为保持不变，受影响的现有测试通过。
- SDK 对象与 wire envelope 不穿透到业务消费者。
- 新增针对 identity、metadata 原样保留、artifact 更新、HITL 和流关闭的 focused tests。
- 可以替换 adapter 内的 SDK 转换而无需让业务层识别 Protobuf 或协议版本。

## 5. 阶段二：升级 SDK 并接入 1.0

### 版本与资料核对

实施时选择支持 A2A 1.0 协议的稳定 Python SDK 1.x release；SDK 版本号和协议版本号分开记录，不要求机械固定为 SDK 1.0.0。

先核对选定 release/tag 的迁移指南、类型、ClientFactory、兼容层与变更记录，检查 Python、Protobuf、HTTP 依赖兼容及相关生命周期脚本。再更新依赖和对应锁文件，不手工修改项目发布版本。不要以 `main/latest` 示例代替所选 release 的实际 API。

### 客户端与转换

- 使用官方 ClientFactory/Client API 替代旧 A2AClient 请求模式，统一覆盖发送、流式、查询、取消和 HITL 续传。
- 在 adapter 内映射 Protobuf message、统一 Part、状态/角色枚举、字段存在性和 JSON 序列化；显式处理文件 raw bytes 与现有内部文件表示，避免重复 base64 编解码。
- 处理 1.0 `supportedInterfaces`、接口协议版本和 endpoint。对支持的 binding 优先选择 1.0；旧 agent 使用官方 0.3 compat。
- 在发送前完成接口选择。已接受任务的查询、取消、续传和恢复保持相同绑定；优先复用现有远端地址/绑定字段，只补足确实缺失的信息，不创建新配置子系统。
- Card 刷新或进程重启不能导致既有任务静默切换到不兼容接口。任何必要的存储字段扩展都要检查已有记录的读取行为。
- 区分明确协议/校验失败与发送结果不确定，保留现有 Execution 的重试和恢复决策权。

### 事件与 webhook

- 原生解码 1.0 StreamResponse 的 task/message/status/artifact 分支，再转换为内部结果。
- 使用正式模型转换替代旧的 proto 形状启发式；不能再依赖 status event 的 `final`。
- `input-required` / `auth-required` 后流关闭保持交互等待；异常断流不能自动完成或盲目重发。
- webhook 的 1.0 StreamResponse 接收、身份关联、去重和 metadata 保留必须验证。官方客户端 transport 的兼容能力不自动覆盖 Hybro 自己的 webhook 路由。

### 0.3 最小保障

使用本地、无 LLM 的 0.3 测试服务，验证旧 Card 可解析、消息可以发送并接收回复。旧服务可运行在独立测试环境，不在同一 Python 环境同时安装两套同名 SDK。

不要求完整验证旧版 streaming、webhook、HITL、文件、取消和恢复。交付时列出未验证路径；发现需要自研兼容才能解决的问题时报告并确认，不自动扩大范围。

### 阶段验收

- 独立的官方 SDK 1.x 测试 agent 可以通过 Hybro 正常注册和调用，而不只是 adapter 单元测试通过。
- 1.0 核心路径满足第 7 节测试要求；0.3 冒烟通过。
- 业务层没有新增协议版本条件分支，前端产品 SSE 不直接暴露 ProtoJSON。

## 6. 阶段三：迁移全部默认 agents

### 共同要求

- 四个 agents 使用支持协议 1.0 的依赖和服务端 API，Card 宣告实际 1.0 接口。
- 将旧 Application wrapper 迁移为选定 SDK release 的 route factories，更新 RequestHandler 构造和 helper imports。
- Task lifecycle stream 先 enqueue Task 再发送更新；message-only stream 遵守单 Message 规则。
- 更新文本、结构化数据、图片/文件、状态与 metadata 构造，保留现有 prompts、工具、交互和错误行为。
- 现有支持的取消行为需保持；原本不支持取消的 agent 不因 SDK 迁移被要求新增该功能，但必须返回正确的协议错误。
- 更新各 agent 依赖、锁文件、启动和测试脚本，消除默认 agent 测试入口中的旧 SDK 固定约束。

### 各 agent 重点

| Agent | 验证重点 |
| --- | --- |
| Story | 初始 Task、最终文本/artifact、任务完成顺序 |
| Travel Planner | input-required、交互 metadata、历史上下文、原任务回答续传 |
| Image Generator | bytes/URL 文件转换、图像 artifact、现有生成/编辑行为及错误 |
| Weather | 第三方 adapter 的 1.0 支持、Card/启动方式、现有天气工具调用行为 |

先确认 Weather 第三方 `a2a-adapter` 是否有适配所选 SDK 的版本。若必须移除或替换它，先说明替代方案与影响并取得确认；不能以此为由静默保留一个旧版默认 agent。

### 与其他工作协调

`docs/llm-runtime-setup-plan.md` 同样涉及默认 agents。A2A 迁移只改变协议接入，不重做 Provider/runtime 接入，也不恢复已被其他工作移除的 Provider 读取逻辑。实施前核对并行变更，每次保持同一工作树单写者。

`default_agents/agents.yaml` 继续作为 manifest 源；需要改变生成配置时修改源并运行 renderer，不直接编辑 Compose 生成区域。

### 阶段验收

- 四个默认 agents 均暴露可调用的 1.0 接口，不把旧 SDK agent 当作兼容捷径。
- 四个镜像构建和启动/导入验证通过。
- 使用 mock LLM、天气 API、存储等验证原有行为，不要求真实付费 Provider 调用。
- 默认 agents 的验证不能替代独立外部 1.0 测试 agent 的接入验证。

## 7. 测试与完成标准

使用现有测试工具，随改动补 focused tests，不建立新的通用测试平台。

### 1.0 必验

- Card 发现、注册、健康检查、接口选择及再次读取。
- 同步 Message/Task 回复、streaming、异步 webhook、GetTask 和 CancelTask。
- 文本、结构化数据、inline bytes、远端文件 URL；metadata 业务键不变。
- artifact 追加/替换、不丢内容、不重复生成最终结果。
- 任务终态、交互等待、流正常结束和异常中断的区别。
- HITL 原任务续传、重复回复处理、关联 identity 保留。
- 任务恢复、重复 webhook、结果不确定时不盲目重发。
- 从请求到 agent、回执、Execution 处理和前端展示的 `client_request_id` 保留。
- 注册 → 调用 → 回复 → 最终落库/展示的本地端到端链路。

### 检查命令和条件

从拥有配置的目录执行：

```bash
# backend/：同步依赖后，执行实际受影响的测试文件
uv run ruff format --check .
uv run ruff check .
uv run pytest <affected-test-files>

# 公共 Protocol 方法发生变化时，同时更新精确 inventory
uv run pytest tests/test_common_foundation.py::test_protocol_methods_match_design_doc

# repository root：默认 agent / Compose 改动
uv run --with pyyaml python default_agents/render_compose.py --check

# repository root：最终差异检查
git diff --check
```

如果 manifest/renderer 输出需要更新，先运行 `uv run --with pyyaml python default_agents/render_compose.py`，再运行 `--check`。

依赖变更使用 `uv sync --extra dev` 更新对应锁文件；冻结环境验证使用 `uv sync --frozen --extra dev`。各默认 agent 在自身配置目录使用其适用命令。

环境可用时，从根目录运行 `docker compose up -d --build` 并验证受影响流程；集成测试必须配置 mock 服务，不能意外请求真实 LLM、天气或其他外部业务服务。环境不可用则记录跳过原因，不声称端到端验收完成。

若实际修改前端，执行 `frontend/AGENTS.md` 要求的受影响 lint/test/build；公开 API 契约改变时，同步 routes/schema tests、`backend/openapi.json` 和前端消费者。不能仅因 SDK 改版就无条件重生成公开契约。

完成需同时满足：阶段一隔离验收、1.0 必验路径、全部默认 agents 迁移、0.3 冒烟及文档更新。存在未通过测试或被阻塞的默认 agent 时，明确报告部分完成，不标记整体完成。

## 8. 文档、交付与需要再次确认的情况

实施过程中按实际行为更新 `backend/docs/System-Architecture.md` 及相关 agent 文档；仅在前端契约/数据流确实改变时更新前端架构文档。架构文档描述当前行为，本计划不提前替换这些描述。

每阶段交付说明包括：修改范围、实际 SDK release 和协议版本、测试结果、未验证路径、依赖/部署影响。保留与本任务无关的修改，不自动提交。

以下情况需再次确认：

- 必须改变产品行为、现有公开 API 或历史数据兼容。
- Weather 第三方 adapter 无法满足 1.0，需要替换或移除。
- SDK 官方 0.3 兼容不满足冒烟，需要自研额外兼容逻辑。
- 需要真实 Provider、付费调用或其他 live integration 测试。
